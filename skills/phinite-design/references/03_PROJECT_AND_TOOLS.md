# 03 · Project layout, `graph_spec.py`, and writing tools

## Layout (created by `kit/new_project.py`)

```
my-usecase/
  graph_spec.py              models, tools, graphs: the single source for deploy
  tools-src/_common.py       shared helpers (copied from kit/tool_common.py, SCHEMA set)
  tools-src/<Graph_Folder>/<tool>.py   one body per tool: docstring + _run(cur, inputs, env)
  tools/…                    GENERATED by kit/build_tools.py; never edit by hand; this is what deploy uploads
  agent-prompts/*.md         prompt text only (one file per master/child)
  db/schema.sql, seed.sql    own Postgres schema: DROP SCHEMA … CASCADE; CREATE SCHEMA …
  demo/simulate.py           reset / log / outbox (+ use-case helpers: simulate human steps)
  demo/smoke_test.py         every tool against the DB, no LLM
  demo/live_e2e.py           (add) the whole story through the deployed graphs + DB checks
  .env                       DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD (git-ignored)
  phinite_ids.json           written by deploy (tool and flow ids)
  README.md, DEMO_RUNBOOK.md, variables.md
```

Older projects (`sba-phase0`, `sba-phase1-simple`) keep `graph_spec.py` under `deploy/`, and their tools were generated from a scratch folder. `kit/deploy.py` supports both layouts; edit their `tools/` files directly.

## `graph_spec.py`

```python
MODELS = {"gemma": {...BYOM block..., "_provider": "byom"}, "phinite": {..., "_provider": None}}
DEFAULT_MODEL = "gemma"
TOOLS = {  # name: (tools/<Folder>, description for the LLM, params (always []), capture vars the tool RETURNS)
  "extract_documents": ("Agency_Review", "Downloads every uploaded PDF … returns document_bundle", [],
                        {"document_bundle": "Chat answers + extracted pages", "review_pass": "Pass number"}),
}
GRAPHS = [{
  "name": "UC - 2 Agency Review", "graphType": "autonomous", "description": "…",
  "masters": [{"id": "review-coordinator", "name": "Review Coordinator", "prompt": "2a_Review.md",
               "tools": ["extract_documents", "complete_review", "route_review"],
               "capture": {"application_id": "Application id in the trigger message"},
               "inputs": ["application_id", "review_reason"]}],          # session variables from the trigger
  "children": [{"id": "document-verifier", "parent": "review-coordinator", "name": "Document Verifier",
                "prompt": "2b_Verifier.md", "llm_tool_description": "Reads document_bundle … stores verification_result",
                "capture": {"verification_result": "JSON …"}, "inputs": ["document_bundle"],
                "resource": "text", "operation": "analysis"}],
  "edges": [("start", "review-coordinator", "submitted"), ("review-coordinator", "end", "routed")]}]
```

- **Tool descriptions** tell the LLM *when* to call the tool and what it returns. Don't list inputs; they come from captures.
- **Graph names** follow `"<UC> - <n> <Name>"` so related graphs sort together.

## Writing a tool (`tools-src/<Folder>/<tool>.py`)

```python
"""my_tool — <Graph> (Phinite tool, no params: reads capture variables from inputs).

What it does, the guardrails it enforces, inputs (captures), env, returns, capture.
"""


def _run(cur, inputs, env):
    cur.execute("SELECT * FROM cases WHERE case_id = %s", (_str(inputs, "case_id") or "",))   # capture or session var
    app = cur.fetchone()
    if not app:
        return _fail("Case not found", "Ask the user for the case id.")      # error + next instruction
    amount = _num(inputs, "loan_amount")                # lenient: "$150k", "150 mil", "1.2 million"
    ...validate first, then write...
    _audit(cur, "my_graph", "ACTION", app["case_id"], {...})
    _notify(cur, "SMS", app["phone"], "Subject", "Body", app["case_id"])     # SMS is really sent via Twilio
    return _ok({"case_id": ..., "message": ...}, {"case_id": ...})          # output, capture_variables
```

Then run `python kit/build_tools.py --project .` and `python -m pyflakes tools` (only "imported but unused" is acceptable).

## Shared helpers (`kit/tool_common.py`)

| Helper | Purpose |
|---|---|
| `_run_tool` / `main` | Connect (env `DB_*`, `search_path=SCHEMA`); run `_run`; **commit on ok, roll back on refusal or error**; log the call to `tool_call_log`; attach `sms_delivery` to the output |
| `_ok(output, capture)` / `_fail(error, next, retryable, **extra)` | The standard result shape (`ok`, `error`, `next`) |
| `_str(inputs, *keys, default)` | First non-empty of several keys (capture names and fallbacks), treats "unknown"/"n/a"/"null" as empty, restores dropped accents |
| `_num`, `_bool`, `_list`, `_code`, `_name_key` | Lenient parsing and normalising |
| `_next_id(cur, table, column, prefix)` | `PREFIX-2026-00001` sequence ids |
| `_audit`, `_notify` | Audit log; outbox, with **SMS through Twilio** (env `TWILIO_ACOUNT_SID`/`TWILIO_ACCOUNT_SID`, `TWILIO_ACCOUNT_TOKEN`/`TWILIO_AUTH_TOKEN`; optional `TWILIO_FROM_NUMBER` or auto-lookup of the account's SMS number; `TWILIO_DEFAULT_COUNTRY_CODE`, default +1; a number starting with `+` is used exactly) |
| `_file_links(inputs)` | File URLs from upload captures and links pasted in chat |
| `_pdf_pages(url)` | Download a PDF and return its text page by page (pypdf, pdfplumber fallback) |

## DB conventions

- **One shared database** (`DB_NAME`, e.g. `sba_uc`), **one schema per use case** (`sba`, `sba0`, …). `demo/simulate.py reset` drops and recreates only its own schema.
- **Required tables** (in the template): `notifications`, `audit_log`, `tool_call_log`.
- **Config in tables, not code:** rules, thresholds, lenders and contacts are seeded in `seed.sql`, so the demo can change a rule without a deploy.
- **Status columns** carry the workflow state. Graphs are stateless between runs, and the DB is the hand-off.

## Documents

Put sample files in `sample-docs/` (a reportlab generator script) and have the user upload them to a public bucket. Keep the URLs in `sample-docs/fileurls.txt`. Text-based PDFs only: there's no OCR in the runtime.

## Knowledge files

Put documents an agent should answer from in `knowledge/` and declare them in `graph_spec.py`:
`KNOWLEDGE = {"Store FAQ": ["knowledge/faq.pdf", "knowledge/policies/"]}` (files or folders), then give the agent
`"knowledge": ["Store FAQ"]`. `deploy_project` creates the knowledge base, uploads files whose names aren't in it yet
and waits for indexing; rename a file to upload a new version. Details: [07 § 6](07_MULTIAGENT_AND_MULTIMODAL.md).

## Use cases without a database

Start from `templates/project_nodb/` (the plugin: `new_project(path, database=false)`). Its `tools-src/_common.py` is `kit/tool_common_nodb.py`: the same `_ok` / `_fail` / `_str` / `_num` / `_bool` / `_list` / `_json` / `_file_links` / `_pdf_pages` helpers, plus `_http` (timeouts and retries), and bodies define `_run(inputs, env)` instead of `_run(cur, inputs, env)`.


API-only use cases (e.g. read GitHub, post to Slack) skip `db/`, `.env` and `demo/simulate.py`. Write a DB-less `tools-src/_common.py`: keep the `# ── shared helpers` marker, keep `_ok`/`_fail`/`_str`, and have `_run_tool` call `_run(inputs, env)` and turn exceptions into `_fail`. `kit/build_tools.py` works unchanged. The smoke test replaces the tool module's `requests` with a fake. Example: `gitupdates/github-slack-daily` (see [06 § API-only](06_LESSONS_LEARNED.md)).
